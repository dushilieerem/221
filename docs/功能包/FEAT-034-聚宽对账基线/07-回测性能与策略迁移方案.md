# 回测性能与聚宽策略迁移方案

> 2026-11-02。回答三个问题：回测为什么慢、要不要换 C++、13 个策略对齐之后事件引擎和策略组的运行方式应该是什么样。

## 1. 现状测量

用 `cProfile` 跑同一段 6 个月回测（2016-09-30 ~ 2017-03-31，同一视图 `research-rv-20261102-21`）：

| 策略 | 优化前（profiled） | 优化后（profiled） | 主要耗时 |
|---|---|---|---|
| 成长多因子 | 140.3 秒 | **77.4 秒** | 因子计算 84 秒 → 29 秒；引擎循环 97 秒 → 43 秒 |
| 三正小市值 | 285.6 秒 | **133.6 秒** | 持仓对象重建与逐日标量查询 |

全区间（2428 个交易日）单策略耗时（6 个并行，有 CPU 争用）：

| 策略 | 耗时 |
|---|---|
| 沪深300增强 | ~12 分钟 |
| 成长多因子 | ~29 分钟 |
| 红利低波+红利成长 | ~46 分钟 |
| 破净组合 | ~67 分钟 |

## 2. 瓶颈在哪

profile 显示的时间分布（优化前）：

| 位置 | 占比 | 原因 |
|---|---|---|
| `get_factor_values` / 因子计算 | 47% | 每次调仓都按全市场重算 TTM 因子；`groupby(...).max()` 落在 object 列上退化成纯 Python 聚合 |
| 逐日标量访问 `frame.at[date, symbol]` | 43%（三正） | `get_current_data` / 涨跌停状态每标的每次都做一次宽表定位，一次 0.2ms，几十万次就是几分钟 |
| `portfolio.positions` 重建 | 44%（三正） | 每次访问都新建 Position 对象并逐个查价 |
| 数据装载与面板构建 | 启动约 60 秒 | 12 个字段 × 5000 列的宽表读取、rename、dict 构建 |

**没有一项是撮合循环本身。** 以成长多因子为例，`_execute` / `_settle` / `_resolved_quantity` 在 77.4 秒的 profile 里合计 0.05 秒。

### 增速差额：单日 30 秒的极端案例

用一周窗口（11 个交易日）做 profile，增速差额单日约 30 秒，全区间自然跑不完。定位后修掉两个逐标的循环：

- `DEGM`（毛利率 TTM 同比）与 `operating_cost_ttm` 每个交易日在 3500 只股票上逐只调用 `_prepare_periods` / `_operating_cost_series`；
- `non_recurring_gain_loss` 逐只对每个标的做 `sort_values`。

改为整表向量化（营业成本按行相减、毛利率用宽表 + 滚动四季求和、非经常损益取每只最新一期），逐值核对 300 只 × 两个报告期与旧实现完全一致。一周窗口从 1944 秒降到 138 秒（profiled，约 14 倍）；未 profile 的一周从 32 分钟降到 1 分 38 秒。

再加「财报快照签名缓存」——同一公告期内因子结果逐日相同，直接复用——一周窗口进一步降到 1 分 29 秒，收益有限：剩余成本已转为逐股健康检查（3.3 秒/天）、MA 价格拉取（2.1 秒/天）和 `get_extras(is_st)` 逐列转换（1.4 秒/天）。这几项都在策略的每日全市场循环里，继续提速需要改策略侧的调用频率或把逐股访问改成宽表。

## 3. 要不要换 C++

结论：**现在不需要，换语言解决不了主要瓶颈。**

- 瓶颈在「重复计算」和「逐点查询」，不在「计算量」。把同样的重复逻辑用 C++ 重写，仍然是重复。
- 已经用纯 Python 手段拿到 1.8–2.1 倍：行缓存（O(1) 查表）、持仓对象复用、因子聚合向量化。这些改动的性质是消除浪费，不是提速常数。
- 真正需要编译核心的场景是**批量参数扫描**：同一策略跑上千组参数、或全市场逐日滚动。这时值得引入 Rust/C++ 内核（Arrow 列存 + 撮合状态机）或直接上 DuckDB/DataFusion 做向量化计算。但那是新的一条链路，不是把现有事件引擎翻译一遍。
- 引入现成引擎（vectorbt / qlib / zipline）成本更高：它们都没有聚宽的 `run_weekly`、`get_fundamentals` PIT、`get_current_data` 语义，兼容层还得重写，等于换一套债。

**建议的优先级**：Python 工程优化（P0/P1）→ 并行与缓存（P2）→ 只有在参数扫描成为刚需时，才做编译核心（P3）。

### 验证

- 同一段 3 个月的三正小市值回测，优化前后逐日权益完全一致（final_equity 与 208 笔成交相同）。
- 字段面板改为 4 线程预读后，两天的空跑启动时间从 52 秒降到 41 秒。
- 成长因子的 TTM 聚合改为向量化后，`total_profit_growth_rate` 与逐标的 `_ttm_at` 手工计算一致（600519 在 2019-09-30 均为 0.2428846709354875）。

### P2（2–4 周）

- 财务查询缓存：单次 `finance.run_query`（利润表 22.6 万行、日期过滤 + 排序）约 200 毫秒；增速差额每天多次查询，是它跑 4 小时以上的主因。按（排序键、可见快照）缓存排序结果，可把这类逐日全市场策略降一个量级。
- 多进程并行：按策略/参数分片，单机 48 核可以直接跑满。
- 结果缓存：以 `FactorBacktestSpec.computation_payload()` 类似的 hash 作为键，重复请求直接返回。
- 任务化：回测提交走队列，避免长任务占满服务进程。

### P3（按需）

- Rust/C++ 核心只覆盖「因子批量计算 + 撮合状态机」，用 Arrow 列存交换数据；Python 保留策略语义层。
- 目标是参数扫描 100 组 < 1 小时，而不是把日频单策略再快一倍。

## 5. 13 个策略对齐后的事件引擎应该是什么样

分四层，边界清晰：

```text
策略层（聚宽源码，原样执行）
        ↓  兼容运行时：g / 调度 / get_price / get_fundamentals / 下单
语义层（口径清单：复权、PIT、涨跌停、行业、分页）
        ↓
事件内核（逐日时钟、撮合、T+1、费用、公司行为、账本）
        ↓
数据层（Arrow 列存、按日分区、视图版本固定）
```

目标状态：

1. **语义可验证**：每个聚宽 API 的行为都有对账用例与金标回归，而不是靠口头约定。`tests/parity/cases/company*` 下的策略用例就是这套回归集。
2. **口径可追溯**：每个结果都带数据视图 ID、代码 hash、参数快照、兼容层版本；同一份输入可复现。
3. **性能有预算**：日频 10 年单策略 < 10 分钟；参数扫描 100 组 < 1 小时；启动 < 10 秒。
4. **边界清楚**：不支持的 API 显式报错（如竞价、分析师），不做静默降级；已知偏差写进报告。
5. **可扩展**：分钟级只要接 1m 数据与新的时点源，不需要改撮合内核。

## 6. 涨跌停数据的接入

数据侧已交付 `derived/limit_prices`（2016-01-19 起，含 `upper_limit/lower_limit/limit_rule`，与 security_master 快照匹配 99.96%）。当前引擎自行按「昨收 × 板块规则」计算，缺 2026-07-06 起主板 ST 5%→10% 这条规则。

接入方式：兼容层 `get_price(['high_limit','low_limit'])` 与撮合限价判断改为优先读 `limit_prices`，缺失时回退现有规则。接入后 2026 年 ST 交易的对账偏差应自然消失。

## 7. 策略组怎么在 SVQuant 上跑聚宽策略

现状：`run_strategy_backtest` 已经能直接执行聚宽源码（`strategy_dialect: joinquant`），CLI 也能跑；但策略组还需要一个可自助的入口。

目标形态（按优先级）：

1. **提交接口**：`POST /api/backtest/strategy` 已存在，扩展 `strategy_dialect=joinquant` + 源码上传；异步契约（202 + run_id + 轮询）沿用现有单因子回测的约定。
2. **参数表单**：区间、初始资金、费率、基准、滑点；其余参数从源码里读默认值，不让用户手填。
3. **结果页**：净值曲线、成交、持仓、指标、对账报告（若提供金标）；失败时返回阶段化错误（哪个 API 不支持、哪期数据缺）。
4. **版本管理**：每次提交保存源码 hash 与数据视图 ID；同一 hash + 同一参数命中缓存。
5. **准入门槛**：静态护栏（禁止网络/文件/子进程）、API 白名单检查、未知 API 显式报错。当前兼容层对未实现 API 抛 `NotImplementedError`，符合这一原则。

接口示例（合成行情有回归用例 `test_joinquant_strategy_runs_through_api`；真实数据视图上用 `TestClient` 提交过一份聚宽源码，2020-01 一个月、`order_target_value` 一笔成交，返回 200 且 `error=None`）：

```bash
curl -X POST http://127.0.0.1:9527/api/backtest/strategy \
  -H "Content-Type: application/json" \
  -d '{
    "strategy_code": "<聚宽源码>",
    "strategy_dialect": "joinquant",
    "engine_mode": "event",
    "timed_execution": true,
    "execution_price_source": "unadjusted",
    "start": "2020-01-02",
    "end": "2026-07-23",
    "initial_capital": 1000000,
    "commission_rate": 0.00012,
    "stamp_tax": 0.001,
    "min_commission": 5,
    "slippage_rate": 0.001
  }'
```

迁移路径：

- 纯 `jqdata` 策略（三正、回购、MA、高斯）→ 现在就能跑（分钟级除外）。
- 用 `jqfactor` 的策略（9 个）→ 因子子集已覆盖，缺的因子按需补。
- 依赖竞价、北向、分析师、回购公告的策略 → 等在数据侧 `UNCOVERED-DOMAINS.md` 里解除；在此之前显式标注不可用。

## 7. 2026-11-11 分钟行情预读与财务预处理缓存

事件回测接上 QuantDB 1m 之后，逐日分钟文件成为单日固定成本：每个交易日的
parquet 有约 2.7 万个 `(symbol, close)` 列，仅页脚解析就要 0.3–0.4 秒，
10 年区间单这一项就超过 15 分钟。

### 改动

- `MinuteStore` 缓存改为保留 Arrow 表：`price_at` 按列名 + 行号直接取标量，
  不再把 2.7 万列转成 pandas；`panel()` 仍按需生成 DataFrame。
- 新增 `MinuteStore.prefetch()`：按交易日顺序用 4 个后台线程预读，最多保留
  4 天在途；事件引擎消费某天后继续提交后续日期，页脚解析与策略计算重叠。
- `finance` 分红预处理帧（61k 行）增加进程级缓存，并按 symbol 只排序一次；
  同一进程内多次策略回测不再重复 11–14 秒的预处理。

### 实测

用例 `value_v3/dividend_v3_10w`，区间 2022-01-04 ~ 2022-03-31（58 个交易日），
同一进程内连续跑两次：

| 版本 | 第一次 | 第二次 |
|---|---|---|
| 改动前（master `1a43ae2`） | 117.0 秒 | 108.5 秒 |
| 改动后 | **73.6 秒** | **58.6 秒** |

两次运行都包含 9.3 秒数据装载启动。仅关闭预读（其余改动保留）时同区间为
121.2 秒，说明预读是主要收益来源；财务预处理缓存主要改善 WebApp 反复提交
短回测的场景（第二次运行少 15 秒）。

### 剩余瓶颈（按 58 日 profile）

| 位置 | 耗时 | 说明 |
|---|---|---|
| 月度选股 `select_stocks_enhanced` | 约 9 秒/次（财务预处理已缓存） | 分红查询、ROE、流动性、波动率 |
| 逐日 `get_industry` | 约 0.17 秒/天 | 每个交易日一次 duckdb 全量扫描 |
| 引擎内部（行缓存、组合估值、分钟取价） | 约 0.4 秒/天 | 已无单项超过 10% |
| 启动装载面板 | 9–12 秒 | 与区间无关的固定成本 |

行业成员快照不能只按「字段值变更」压缩：标的退出/移出快照时值不变但
presence 变化，简单 change-log 会把退市股带进后续日期，已放弃该方案。

## 8. 2026-11-11 第二轮：按需列读取、行切片与少量标的行业缓存

#44 之后分钟读取仍是逐日固定成本；进一步定位到三处可避免的重复工作：

- **分钟列惰性读取**：单日 parquet 有 2.7 万列，打开时只解析页脚与索引，
  标的列在第一次用到时才按列读取（复用已解析 schema），不再整行读 close。
- **行切片**：`history` / `limit_panel` 用布尔 `loc` 切「全历史 × 5000 列」
  面板，每次约 22 毫秒；改为 `searchsorted + iloc` 后约 0.1 毫秒。
- **少量标的行业**：持仓只有十几只，`get_industry` 原先每天做一次全量快照
  扫描（0.18 秒）；改为按 symbol 拉一次全历史（含退市 presence 语义），
  逐日只查快照当日。
- 行缓存改存 Series（不再 `to_dict()` 整行）；盘中价按 (日期,时点,标的)
  缓存；预读窗口 8、8 线程。

同一 58 日用例（`dividend_v3_10w`，2022 Q1，含 9 秒启动）：

| 版本 | 第一次 | 第二次（进程内） |
|---|---|---|
| master `1a43ae2`（本轮前） | 117.0 秒 | 108.5 秒 |
| 本轮改动 | **65.5 秒** | **48.3 秒** |

净值指纹与改动前完全一致（58 日 `final_equity=97346.729693`，29 笔成交）。

## 9. 2026-11-11 完整 10 年实测与 numba 内核评估

同一用例 `value_v3/dividend_v3_10w`，2016-09-30 ~ 2026-09-30（2428 个交易日，
1681 笔成交），固定视图 `research-rv-20261111-3`：

| 版本 | 回测耗时 | 启动 | `final_equity` | 净值 sha256（前 8 位） |
|---|---|---|---|---|
| master `1a43ae2`（本轮优化前） | 3485.4 秒（58.1 分钟） | 9.3 秒 | 432888.13541179977 | `7999d0aa` |
| 第二轮优化后 | **1036.6 秒（17.3 分钟）** | 9.1 秒 | 432888.13541179977 | `7999d0aa` |

- 整体 **3.36 倍**，成交笔数与净值曲线逐位一致。
- 58 日短区间从 117.0/108.5 秒降到 66/47 秒；长区间收益主要来自分钟列惰性读取与预读、
  行切片和行业/停牌按日缓存，而不是策略代码本身的改动。

### numba 内核评估

按计划引入 `app/services/strategy/event/kernels.py`（`RE_NUMBA_KERNELS=1` 时启用，
默认关闭）：

- `limit_price_values` 单点比 numpy 快约 2 倍（780×5000 窗口 28ms vs 61ms）。
- 整跑 58 日稳态：numba 45.5 秒 / CPU 107 秒，纯 numpy 43.3–44.6 秒 / CPU 107–110 秒，
  差异在噪声范围内；首次调用额外承担约 20 秒 JIT。
- 尝试的「持仓批量取价」路径反而从 5.9 秒变 7.7 秒（缓存命中被绕过、预读滞后），已回退。

结论：当前瓶颈是聚宽策略回调里的 Python 对象与循环，不是可编译的数值循环；
numba 保留为显式开关，默认走纯 numpy。要把 10 年压到 10 分钟内，仍需策略向量化
（另立计划），而不是继续增加内核。

基准工具：`tools/benchmark_event_backtest.py`，支持固定区间、重复次数、固定
`--data-dir` 与 `--profile`，输出 wall/CPU、成交数、`final_equity` 和净值 sha256。
